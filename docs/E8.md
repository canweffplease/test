# E8: do the congestion-control rankings hold across transfer sizes?

**Question.** Do the policy rankings and the distance-from-floor numbers from
E3 still hold when the KV-transfer size distribution changes? We tested
fixed 4K prompts, Azure conversation-trace and code-trace prompt lengths, and
a model with 2.5x the bytes per token.

**Short answer.**

- **The p50 ranking holds:** EQDS < HPCC < RoCE < DCQCN in all 6
  Llama-3-70B cells (3 regimes x loads 50/70). EQDS is first in every one of
  the 8 cells, with disjoint seed ranges and 3/3 paired seeds.
- **It changes in two places, and both changes are within seed spread.**
  1. With Llama-2-13B (2.5x bytes) DCQCN climbs from last to tied with
     RoCE and HPCC.
  2. On the code trace at load 70, EQDS loses the p99 to HPCC (13.98 vs
     12.27). EQDS's p99 there is set by 13-33-token prompts that pay
     90-220 us.
- **Making requests bigger at the same load leaves EQDS, HPCC and RoCE
  exactly where they were.** Their x_floor is flat: the paired 13B/70B ratio
  is 0.99-1.00 and their excess time grows 2.48-2.50x for 2.5x bytes. Their
  costs at load are proportional to size. **DCQCN is the only policy whose
  x_floor falls** (ratio 0.80, excess x1.93-1.96). Part of its cost is a
  fixed recovery time.
- **Small requests do not change the order, but they spread the policies
  apart.** On conversation prompts (median 1K tokens) DCQCN goes from 4.7x
  to 14.7x the ideal fabric. RoCE goes from 3.8x to 6.1x, and EQDS stays at
  1.3-1.5x.
- **Isolated requests (one request alone on the fabric, separately fitted)
  confirm the split.**
  - RoCE: 13 us fixed, then its ECMP class (2.04x), size invariant.
  - HPCC: 36 us fixed, then 2.18x (RoCE's class / eta).
  - EQDS: 29 us fixed, then 1.31x.
  - DCQCN: non-monotonic. It matches RoCE below about 3 MB per shard, then
    gets 6-6.6x at 10-42 MB per shard, and falls to 2.8x at 419 MB.

Everything is on the 16-node default fat tree, 400 Gbps, main build
(`HTSIM_BUILD=build`), all four policies paper-faithful (HTSIM/OUR_CHANGES.md,
"Summary of changes").

Notes on the matrices:

- **Request counts.** The conversation trace's mean request is 0.378 GB, so
  there are 3.5x as many requests as fix4k, not 4x. The code trace (mean
  0.671 GB) has 2x as many. Prompt lengths sampled in the conv matrices:
  min 22, median 1,020-1,037, max 4,118 tokens. Code: min 13, median
  1,890-2,064, max 7,436.
- **No clamping was needed.** The largest code prompt (7,436 tokens) is
  304,578,560 B per shard, below 2^31-1. `--max-prompt` was not used.
- **Realized load differs from target in the trace regimes.** `--fix-count`
  fixes the request count (`gen_workload.py:623-625`), not the bytes, and
  the sampled sizes land off the mean: conv 50 is 0.396, code 50 is 0.650,
  code 70 is 0.787. That is why every comparison below is also made against
  the policy-independent fluid ideal on the same matrix (`x_ideal`,
  `scripts/exp_report.py` `fluid()`). x_ideal removes the queueing that any
  fair network would impose at that realized load.
- **Arrival process, not trace arrivals.** All regimes use the same Poisson
  process. The code trace's burstiness (inter-arrival CV 13.2) is
  deliberately *not* reproduced, so that only the size distribution changes.
- **Why l13b uses a 250 ms window, which deviates from the brief's wording.**
  "Same count and arrivals" and "same load" are incompatible at 2.5x bytes:
  at the fix4k rate, 13B would be 1.26x / 1.76x overload. So the window is
  stretched 2.5x. `--fix-count` draws `sorted(rng.uniform(0, window))`
  before any prompt (`gen_workload.py:625`, prompts at `:633`), so with the
  same seed every arrival time is exactly 2.5x the fix4k one. Count (15/21),
  load (0.503/0.705) and the arrival pattern in units of the floor are all
  identical, and request ids pair one-to-one. Only the bytes change.
- **fix4k was rerun, not reused.** `results/e3/ft16/` has no DCQCN summaries
  at loads 50/70, and its other runs came from older builds (`build_start`,
  `build_eqds2`, `build_hpccfix`). The main build reproduces those E3 runs
  exactly: RoCE 11.94 / 8.65 / 7.27, EQDS 3.41 / 3.40 / 3.52 and HPCC
  9.36 / 7.22 / 7.74 p50 at load 70, seeds 1-3.

**Isolated size ladder** (`./scripts/e8.sh iso`). One TP=8 request alone at
t = 0 with 16, 64, 256, 1,024, 4,096 and 7,436 tokens on Llama-3-70B, plus
4,096 on Llama-2-13B (0.66 to 419 MB per shard). Seeds 1-5,
`workloads/e8/iso/`, results in `results/e8/iso/`. This separates fixed from
proportional cost with no load at all.

**Validity.**

- All 96 load runs and all 140 iso runs are complete: every flow finished,
  0 lossless violations, start skew 0.000 us.
- **Every DCQCN cell uses the clamped binary** (minimum rate at one R_AI
  step, commit 4d3e1b2; HTSIM/OUR_CHANGES.md, "DCQCN: minimum rate clamp").
  Before the clamp `dcqcn_default_l13b_load50_r2_s2` aborted in the
  simulator (see "A DCQCN simulator crash"). All 24 DCQCN load runs were

## Why

### 1. RoCE: the cost is placement, so x_floor is size invariant. Confirmed

**In isolation**, RoCE sends at line rate from the first packet
(`_pacing_rate = rate`, roce.cpp:78). Each flow keeps the one path its
`_pathid = random()%256` hashes to (roce.cpp:66). Completion is therefore
(collision class) x floor plus a constant:

- The fit gives a = 13 us and b = 1.03, i.e. the 2-way class at
  2.03-2.04x. That class is the same at 42 MB and at 419 MB per shard.
- The seed with a 3-way collision gives 3.05-3.06x at every size from
  42 MB up.
- Only below about 10 MB per shard does the constant (propagation plus a
  few packet times) show, as 2.46x at 2.6 MB and 3.24x at 0.66 MB.

**Under load**, the paired 13B/70B x ratio is 1.00 at both loads, and the
excess grows 2.49-2.50x. In the trace regimes, RoCE's x_ideal is flat
across prompt-length bins (`results/e8/e8_sizebins.md`):

- conv: 6.25 / 6.42 / 5.86 / 7.87
- code: 4.88 / 3.09 / 4.87 / 5.20

RoCE's x_floor is higher for small requests (15.1 vs 10.5 on conv), but
the ideal fabric shows the same gradient (2.69 vs 1.31). Under fair sharing,
a short request that lands in a busy period is slowed by everyone present,
while a long one averages over arrivals and departures. That gradient is
the workload's, not RoCE's.

### 2. DCQCN: startup collapse plus a slow recovery, a fixed time cost with a hump

A new DCQCN flow starts at line rate with alpha = 1 (`_RC = rate`,
`_alpha = 1`, dcqcn.cpp:51-55). Each CNP sets `_RC = _RC * (1 - a/2)`
(dcqcn.cpp:84-85), and the sink sends at most one CNP per 50 us
(dcqcn.cpp:20). Recovery is fast recovery followed by additive increase of
R_AI = 0.1 % of line rate per step (dcqcn.cpp:32, 121-135), on a 55 us timer
(dcqcn.cpp:21).

A rate trace from the crashing run (`DCQCN_TRACE=1`, seed 2, l13b load 50;
`Roce_7_15`, which is a source on host 7) shows the shape. Under load the
rate goes 400 -> 201 -> 101 -> 51 -> 26 -> 13 -> 6.5 Gbps in 250 us, one
halving per CNP interval while alpha stays at 0.99. It then climbs
+0.4 Gbps per 55 us, which is 7.3 Gbps per ms, so recovering to line rate
takes tens of milliseconds.

The isolated ladder shows what this does to size:

- **Tiny requests are unaffected.** At 0.66 and 2.6 MB per shard (13 and
  52 us floors) the flow finishes before the first CNP can come back, so
  DCQCN equals RoCE exactly (3.24, 2.48).
- **Medium requests are the worst case.** At 10-42 MB per shard (0.2-0.8 ms)
  the flow is cut within its first ~100 us and never recovers before it
  ends: 6.0-6.6x, three times RoCE's collision class.
- **Large requests amortize it.** They spend most of their life climbing
  back: 3.44x at 168 MB, 2.77x at 419 MB.

The excess (right panel of `e8_iso_size`) rises much faster than slope 1
between 52 us and 840 us floors, then parallels slope 1. The fit gives
a = 906 us of fixed cost per request, which is a recovery time, not a byte
count.

**At load the fixed part is larger and makes DCQCN the only policy whose
x_floor falls with size.** The 13B/70B excess ratio is 1.93-1.96, against
2.5 for a purely proportional cost. A two-point fit (excess = a + b x floor)
gives a fixed part of roughly 8-13 ms per request, against 16-23 ms of
proportional cost on the 70B floor. That is the recovery time scale above.
This is why DCQCN moves from clearly last to tied with RoCE and HPCC on
Llama-2-13B: x_floor 12.19 -> 8.96 at load 70, while everyone else stays put.

**Small requests make DCQCN much worse, because cuts scale with flow
arrivals, not bytes.** Every new flow re-enters at line rate
(dcqcn.cpp:51). With 3.5x more requests at the same byte load (conv), 3.5x
as many line-rate bursts hit queues that the existing flows are sharing.
Each burst marks packets (RED from Kmin = 50 KB,
queue_lossless_output.cpp:50-52), and the marks send CNPs to every flow on
that queue, including old ones that were climbing back. DCQCN's x_ideal goes
4.72 (fix4k) -> 7.19 (code) -> 14.68 (conv) at load 70. Its backlog shows up
as 13.0 concurrently active flows per NIC on conv, against 5.0 on fix4k.

### 3. HPCC: per-flow placement divided by eta, plus a newcomer advantage that hurts long requests

**In isolation**, HPCC starts each flow at W_init = T x line rate
(hpcc.cpp:91), which is line rate. Its first ACK only stores the INT
reference (hpcc.cpp:274-279). It hashes like RoCE, and then holds every link
at eta = 0.95 (hpcc.cpp:38, 585-586). Its large-request x is 2.18, i.e.
RoCE's 2.04 class / 0.95 = 2.15, with fit b = 1.17 and a fixed cost of
36 us. Both of HPCC's costs in isolation, the collision class and the 5 %
headroom, are proportional.

**Under load**, HPCC is also proportional (13B/70B ratio 0.99, excess
x2.48). It is the one policy whose x_ideal *rises* with request size:

- conv: 4.13 (<= 512 tokens) -> 4.69 -> 6.10 -> 7.45 (> 4,096)
- code: 2.50 -> 3.28 -> 3.72 -> 4.35

The cause is how the window moves:

- A newcomer enters at W_init, i.e. line rate.
- A flow that has been squeezed recovers only by
  W_AI = W_init (1 - eta) / N (hpcc.cpp:116; N = 10, so 0.5 % of the BDP)
  per update.
- The reference window Wc moves once per RTT (`updateWc`,
  hpcc.cpp:286-289).

Every arrival therefore takes bandwidth from flows already in progress, and
the longest requests live through the most arrivals. OUR_CHANGES.md
("HPCC: from a compounding window...", validation a) records the same
newcomer advantage in the convergence test.

That is why HPCC has the highest Jain index in the trace regimes (0.87 /
0.93) and the best p99 on code 70. Its x is nearly flat across sizes,
because it penalizes large requests rather than small ones.

### 4. EQDS: a fixed startup cost that only matters for tiny prompts

**In isolation**: a = 29 us, b = 0.31, and x is 1.31 from 42 MB up.
The fixed cost is the credit loop:

- The source sends a speculative first window of 64 packets
  (`DEFAULT_CWND`, main_eqds.cpp:33, set at :573-574; `_credit_spec = _maxwnd`
  in `startFlow`, eqds.cpp:968-1006). That is 265.6 KB, or 5.3 us at 400 G.
- Everything after it must be pulled by the receiver's pacer
  (eqds.cpp:2219).
- The first pull cannot arrive before one cross-pod RTT (about 13 us), so
  every flow idles for roughly an RTT minus 5 us at its start.
- Trimmed packets come back by NACK plus pull, which is another round trip
  at the tail.

At 0.66 MB per shard that is 2.78x, against a 1.50x propagation bound. At
10 MB it is 1.51x. The proportional part (1.31x) does not change with size.
It covers headers (64 B per 4 KB), pulling at just under line rate
(eqds.cpp:2219) and per-packet spraying collisions with trims. EQDS
retransmits 2.5-4.2 % of packets in every regime and load (`log_counters`
`rtx_pkts` / `new_pkts`: 3.3-4.1 % fix4k 70, 3.2-3.4 % conv 70, 3.4-4.0 %
code 70, 3.5-4.2 % l13b 70), i.e. in proportion to bytes, not to flow
count.

**Under load**, EQDS is proportional (13B/70B ratio 1.00, excess x2.49).
Its x_ideal stays at 1.27-1.47 in every regime, so spraying keeps it within
30-50 % of a perfect fabric whatever the size mix.

The exception is tiny requests on a busy receiver:

- In code 70 the worst EQDS request in every seed is a **13-token prompt**
  (532 KB per shard, floor 10.6 us) at 14.6-17.5x, against an ideal of
  4.0x. The next worst are 14- and 33-token prompts at 7-10x.
- Their excess is only 90-220 us. The speculative window lands on a
  receiver downlink that the pull pacer already keeps at line rate for
  other flows, gets trimmed, and is resent via NACK plus pull, while the
  pacer round-robins credit among the active sinks.
- That ~0.1-0.2 ms is irrelevant for TTFT, but on a 10 us floor it is the
  run's p99.
- So EQDS's code 70 p99 (13.98) is set by prompts under 40 tokens, while
  HPCC's p99 (12.27) is set mostly by 1.3K-4.3K-token requests.

The p99 "loss" to HPCC is a property of the metric (dividing by a floor
smaller than one RTT), not a tail-latency problem.

### 5. Jain's index differs between regimes because it measures size dependence

parse.py computes Jain over completion / prompt_tokens (parse.py:413-414).
Because floor = ceil(P x bytes_per_token / T) x 8 / link
(gen_workload.py:584-585), that index is the same as Jain over x_floor up to
rounding: the two columns of `e8_table.md` agree to 0.001.

- **Fixed-size regimes.** Every request has the same floor, so Jain only
  measures spread from queueing and placement: 0.88-0.98 for every policy,
  identical between 70B and 13B.
- **Trace regimes.** Jain also measures how x depends on size:
  - It falls most for EQDS (code 0.68, conv 0.80). Its x is small for large
    requests (1.93 above 4K tokens on code) and large for tiny ones (5.3 at
    512 tokens or fewer, up to 17).
  - HPCC stays high (0.87 / 0.93) because its x is flat in size, for the
    reason in point 3.
  - The fluid ideal itself is not size-flat: on conv its p50 by bin is
    2.69 / 2.33 / 1.65 / 1.31. A Jain value below 1 in these regimes
    therefore does not by itself mean a policy is unfair.

In these regimes, Jain over prompt-normalized TTFT rewards a policy that
slows long requests as much as short ones (HPCC). It penalizes one that
finishes long requests near the floor and short ones with a fixed ~0.1 ms
overhead (EQDS).

### 6. Deadline miss (2 x floor)

- **Unchanged by size wherever size is the only change.** Between fix4k and
  l13b the rates are identical for every policy: EQDS 0.81 / 0.60 at loads
  70 / 50, everything else 1.00.
- **HPCC, RoCE and DCQCN still miss 100 % in every regime**, as in E3, since
  one 2-way collision is already 2.03-2.04x. The exceptions are 0.98 for
  HPCC and RoCE on conv 50.
- **EQDS's miss rate becomes size dependent.** On code 70 it is 0.92 for
  prompts of 512 tokens or fewer, 0.78-0.81 in the middle bins and 0.43
  above 4K tokens: small requests miss because of the fixed cost in point 4.
- **The trace regimes widen EQDS's gap to the ideal**, because the ideal
  misses less on small-request mixes:

  | load 70 | EQDS miss | ideal miss |
  |---|---|---|
  | conv | 0.82 | 0.58 |
  | code | 0.76 | 0.64 |
  | fix4k | 0.81 | 0.71 |

### 7. With many small overlapping requests, ECMP collisions average out per placement but cost more on average

E3 found RoCE's cost to be discrete collision classes (1x / 2x / 3x) plus
host-wide PFC pauses. When the host NIC is paused, every source on the host
stops (queue.cpp:461-466). With small requests there are more concurrent
flows per NIC:

| load 70 | busy-period average active flows per sending NIC | RoCE p50 x_ideal | RoCE p50 seed range (relative to median) |
|---|---|---|---|
| fix4k | 3.9 | 3.80 | 54 % |
| code | 4.9 | 4.82 | 37 % |
| conv | 5.8 | 6.07 | 34 % |

Two effects show up at once:

- **Averaging.** Each new flow re-draws its path (roce.cpp:66). With more
  flows per uplink, the per-seed placement lottery matters less: the seed
  range shrinks from 54 % to 34 %, and the scatter in
  `e8_scatter_code_load70` is continuous rather than banded.
- **More collisions and more coupling.** The cost against the ideal rises
  (3.80 -> 6.07). With more flows on a host, it becomes more likely that at
  least one of them is on a congested uplink and pauses the whole NIC.

HPCC, which also uses one hashed path per flow, follows the same direction
(x_ideal 3.24 -> 4.50). EQDS, which sprays per packet, barely moves
(1.28 -> 1.47). So collisions still dominate for per-flow-path policies when
small requests overlap. More flows turn the discrete classes into a higher,
less seed-dependent mean, not into a fair share. We did not rerun
`scripts/pfc_diag.sh` on these matrices, so the pause-coupling part is
inferred from E3's mechanism and these aggregates, not measured directly
here.

### 8. Llama-2-13B vs Llama-3-70B 4K, and what it means for long-context serving

Same flows, same arrivals in floor units, 2.5x bytes:

| policy | how x_floor moves at 2.5x bytes | dominant cost |
|---|---|---|
| EQDS | flat (1.00) | proportional: sharing at the receiver pacer, plus spraying, trims and headers at 1.31x |
| HPCC | flat (0.99) | proportional: per-flow ECMP class / eta, and sharing with the newcomer bias |
| RoCE | flat (1.00) | proportional: ECMP class and PFC pause coupling |
| DCQCN | falls (0.80) | partly fixed: rate-recovery time after the startup cut (~1 ms alone, ~10 ms under load) |

**Longer contexts are not amortized by the network.** For EQDS, HPCC and
RoCE, every extra token costs the same multiple of its floor:

- EQDS's median network excess at load 70 goes from 8.1 ms to 20.0 ms when
  the cache grows 2.5x. HPCC goes from 23 ms to 57 ms, RoCE from 27 ms to
  72 ms.
- Long-context serving therefore pays network TTFT in proportion to context
  length, and the policy ratios (EQDS 1.9-3.1x better than HPCC at the median) carry over unchanged to longer contexts.
- Startup costs (EQDS 29 us, HPCC 36 us, RoCE 13 us) only matter below about
  10 MB per shard, i.e. prompts of about 250 Llama-3-70B tokens or fewer.

DCQCN is the only policy that improves with size. That is not a reason to
prefer it for long contexts: at 13B it only catches up to RoCE (which has no
congestion control) and HPCC, still 2.5x worse than EQDS. For short,
chat-like prompts (the conv regime) it is the worst choice by a widening
margin (x_ideal 14.7).

## A DCQCN simulator crash (one run, not a result)

`dcqcn_default_l13b_load50_r2_s2` aborts at simulated time 121.9 ms with
`roce.cpp:341: RoceSrc::doNextEvent(): Assertion 'next_send > eventlist().now()' failed`.
It did so at END 1, 2 and 4 s alike, because the run is deterministic. The
crashing log and the partial summary (`_summary.incomplete.json`) are in git
at commit bd0af76; the clamp commit replaced them.

The cause, from a `DCQCN_TRACE=1` rerun:

- One `Roce_7_15` flow received a CNP every 50 us for about 2.4 ms. Its rate
  went 0.63 Gbps -> 0.0137 -> 1e-6 -> 1 bps -> **0**.
- `_RC` is a `linkspeed_bps`, which is `uint64_t` (config.h:44), so
  `_RC * (1 - a/2)` (dcqcn.cpp:85) truncates to 0 after about 39 halvings.
- There is no minimum rate.
- `update_spacing()` then divides by a zero `_pacing_rate` (roce.h:48), and
  the spacing assertion fires.

Marks keep arriving although the flow is sending almost nothing. That is
consistent with packets it sent earlier still sitting in deep queues, i.e.
stale feedback. The DCQCN paper's deployments, and the ns-3 reference code,
clamp the rate at a minimum. `dcqcn.cpp` now clamps `_RC` at one R_AI step
(commit 4d3e1b2; HTSIM/OUR_CHANGES.md, "DCQCN: minimum rate clamp"). The
run completes, the l13b load-50 cell has three seeds, and every E8 DCQCN
run was rerun on the clamped binary. The clamp is not bit-identical
elsewhere: it acts whenever a cut would go below R_AI.
