# E2: topology vs load

**Question.** How much does fabric oversubscription (1:1, 4:1, 8:1) cost a
KV-cache transfer at a given offered load, and how much of that cost is the
oversubscription itself versus the transport's handling of it?

**Status.** RoCE (PFC only, no CC), HPCC, EQDS and DCQCN done, 3 seeds,
5 matrices x 3 topologies plus the PFC victim-flow micro-test. Every run is
complete and has zero lossless violations.

Two notes on how the runs were made:

- **EQDS 8:1 interleaved load70.** run.sh was edited while these three
  runs were in flight (commit ca6d474, comment-only, 22:45). Its
  post-processing then failed with a syntax error after the simulations had
  finished. The three logs were parsed afterwards with run.sh's own
  `parse.py` call and `scripts/explib.sh`'s post step, so their summaries
  are the same as a normal run's.
- **DCQCN.** The tables use the binary with the minimum-rate clamp (commit
  4d3e1b2). The earlier, unclamped sweep is in `results/e2/dcqcn_preclamp/`.
  One of its runs never finished ("Why (DCQCN)" point 4).

## Setup

All three trees are 128 hosts, 4 hosts per ToR, 16 per pod, 8 pods, 100 Gbps
links (`HTSIM/htsim/sim/datacenter/topologies/fat_tree_128_<x>os.topo`):

| topology | ToR up | agg up | pod -> core | where it is oversubscribed | one TP = 8 request alone (iso bound) |
|---|---|---|---|---|---|
| 1:1 (`fat_tree_128_1os`) | 4 x 100 G | 4 x 100 G | 1,600 G | nowhere | 1 x floor |
| 4:1 (`fat_tree_128_4os`) | 4 x 100 G | 1 x 100 G | 400 G | agg -> core (tier 1 `Oversubscribed 4`, `Radix_Up 1`) | 2 x floor: 8 shards (800 G) leave the pod through 400 G |
| 8:1 (`fat_tree_128_8os`) | 1 x 100 G | 2 x 100 G | 800 G | ToR -> agg 4:1 and agg -> core 2:1 | 4 x floor: the 2 ToRs of an instance have 200 G of uplink for 800 G |

**Effective load.** The `--load` label is load on the 1:1 tree. The
generator's sidecar (`also_topo` in each `.json`) gives the load on the
binding resource of the other trees:

| matrix | 1:1 | 4:1 (binding: pod up/down) | 8:1 (binding) |
|---|---|---|---|
| interleaved load30 | 0.30 | 0.60 | 1.21 (ToR up/down + pod up/down) |
| interleaved load50 | 0.50 | 1.01 | 2.01 |
| interleaved load70 | 0.70 | 1.41 | 2.82 |
| split load30 | 0.30 | 1.21 | 2.42 (pod up/down) |
| split load50 | 0.50 | 2.01 | 4.03 |

The "0.30 / 0.60 / 1.21" ladder holds only for the interleaved matrices: in
the split matrices only pods 0-3 send, so their pod uplinks carry twice as
much. Effective loads above 1 mean the arrival window is longer than the
fabric can drain; requests queue and the run lasts beyond the 50 ms window.

**Buffer size.** `run.sh`'s `ft128_1os` / `ft128_4os` aliases use `-q 500`,
which loses PFC losslessness on these 4-host ToRs (10^4 - 10^5 "LOSSLESS not
working" lines, `queue_lossless_output.cpp:91`, all on ToR uplinks). Those
runs are invalid and kept for reference in `results/e2/q500_invalid/`. A
ToR or agg has 8 ingress ports, each allowed 150 packets plus headroom
before PAUSE (`main_roce.cpp:345`), so an egress can be asked to hold about
1,240 packets. The scripts pass topologies by file name, which `run.sh`'s
generic branch runs with `-q 2000`, the value `ft128_8os` already used
(`scripts/explib.sh`, `run_topo`; `FT128_ALIAS=1` restores the aliases).
Buffers are therefore matched across all three trees.

**`-linkspeed`.** `run.sh` now passes `-linkspeed $((GBPS*1000))` with GBPS
read from the topology file (100000 here). Every run in this document was
made after that change.

Metrics (`scripts/exp_report.py`): per request, slowest shard.
`x_iso` = completion / iso bound, the oversubscription-adjusted bound of a
request alone on that tree. `ideal` = completion in a fluid max-min fair
fabric with the same aggregate resources, perfectly balanced, carrying the
whole matrix; `x_ideal` = completion / ideal. Both are policy independent,
so x_ideal = 1 means the policy wasted nothing.

Reproduce:

    POLICIES=roce  HTSIM_BUILD=build_start   VICTIM=1 ./scripts/e2.sh 3
    POLICIES=hpcc  HTSIM_BUILD=build_hpccfix VICTIM=1 ./scripts/e2.sh 3
    POLICIES=eqds  HTSIM_BUILD=build_eqds2   VICTIM=1 ./scripts/e2.sh 3
    POLICIES=dcqcn HTSIM_BUILD=build         VICTIM=1 ./scripts/e2.sh 3

`e2.sh` takes the 1:1 split runs from `results/e3/ft128_1os/` when that
policy's summaries are there (run `./scripts/e3.sh ft128_1os 3` first to
avoid running them twice) and runs them itself otherwise; `REUSE_E3=0`
always reruns them. `VICTIM=1` is the default; `VICTIM=0` skips the
micro-test.
It skips runs whose summary exists and rewrites `results/e2/e2_table.{md,csv}`,
`results/e2/e2_victim.{md,csv}`, `results/figs/e2_topology.png` (interleaved)
and `results/figs/e2_topology_split.png` from every summary present.
PFC diagnostics (`scripts/pfc_diag.sh`, seed 1) are in `results/e2/diag/`.

(completion > start + 2 x floor) is left out. It is 1.00 in every RoCE,
HPCC and DCQCN run and in every EQDS run on 4:1 and 8:1, where the iso bound
is already >= 2 x floor. It is 0.00 in every EQDS run on 1:1. Rtx is 0 for
RoCE, HPCC and DCQCN; EQDS's retransmissions are in "Why (EQDS)" point 2.

## Why (RoCE)

### 1. 4:1 binds for every request, at every load

The 4:1 tree has one 100 G core uplink per agg, 400 G per pod. A TP = 8
instance's 8 cross-pod shards want 800 G, so even alone a request takes 2 x
floor (iso = 2); the generator's sidecar lists the binding resource as
`pod_up, pod_down`. So 4:1 is not an aggregate-load effect: at interleaved
load30 the pods' uplinks are only 60% loaded, yet the ideal p50 and p99 are
both exactly 2.00 = iso. Every request is bound by the pod uplink.

RoCE at that point is 4.13 x floor = 2.06 x iso, almost exactly its
1:1 result on the same matrix (2.12 x floor = 2.12 x iso). The
oversubscription and RoCE's own inefficiency multiply. From 50% (effective
1.01) upward requests also queue behind each other in the ideal (2.26,
3.09), and RoCE's x_ideal stays at 2.5-2.6.

### 2. Why RoCE wastes less on more oversubscribed trees

x_ideal at the median, interleaved load70: 3.51 (1:1), 2.52 (4:1), 1.43
(8:1); split load50: 4.05, 1.44, 1.18. RoCE's absolute numbers get worse
(12.7 x floor at 8:1 load70), but its waste relative to a perfect transport
shrinks as the fabric becomes the bottleneck.

The waste is ECMP collisions (E3 point 1: one path per flow,
`_pathid = random() % 256` at roce.cpp:66, hashed at
fat_tree_switch.cpp:339, no rate control, roce.cpp:310-344). On 1:1 the
collided link is the only bottleneck, so a 2-way collision costs 2x and a
3-way 3x relative to an ideal of 1. On 4:1 a flow can still pick its agg
(4 ToR uplinks), so collisions concentrate shards on some of the 4 agg -> core
uplinks while others idle: at load70 those uplinks range from 0.10 to
0.82 utilization (median 0.44) although the pod is 1.41x overloaded. On
8:1 a ToR has a single uplink: every flow of the ToR shares it whatever the
hash, as an ideal fabric would, and the FIFO egress gives each of the 4 host
ingress ports an equal share (the per-port sharing E6 measured exactly). Only
the agg's 2 core uplinks are left to collide on. Fewer path choices means
less path lottery; as in E6, when the bottleneck is unavoidable the hash
stops mattering.

### 3. Pauses on oversubscribed trees idle the bottleneck itself

The bottleneck links are not kept full. On 8:1 the 16 busy ToR uplinks
are 44% (load30) and 68% (load70) utilized at the median over the run, and
for 26-28% of the time they had packets PFC kept them silent. That is
direct waste on the scarcest link of the fabric. The mechanism is
head-of-line blocking one hop up: an agg's ingress counter for a ToR port
fills with packets for whichever of its 2 core uplinks a collision
overloaded (agg uplinks 0.18-0.91 utilization), and the counter is
released only when a packet leaves that egress
(queue_lossless_output.cpp:152). It passes 150 packets and pauses the ToR
uplink (queue_lossless_input.cpp:70-72, thresholds main_roce.cpp:345), and
a paused LosslessOutputQueue stops all its traffic, one class
(queue_lossless_output.cpp:50-57), including packets for the idle core
uplink. The same happens on 4:1 one hop lower: the ToR uplinks (not the
bottleneck) are paused for 37-45% of their backlogged time because the agg
ingress behind them is full of packets for a congested agg -> core uplink.

Host NICs are paused most of all (0.42 at 8:1 load30, 0.60 at 4:1 and 0.80 at
8:1 load70). The NIC forwards a PAUSE to every RoceSrc on the host
(queue.cpp:461-466) and stops service (queue.cpp:516-519), and its queue never
drops (queue.cpp:480-484), so at high effective load each host holds
tens of thousands of packets (up to 68,000 at 4:1 load70) that then wait on
the slowest path any of them uses.

### 4. RoCE victim flows

PFC's known failure is that pauses caused by one congested egress stop
unrelated traffic. The micro-test isolates it: six congestors push 600 G from
pod 0 to pod 4 (through 400 G of agg uplink on 4:1) while the victim 3 -> 15
stays inside pod 0 and crosses no oversubscribed link. Alone it takes
1.02 x floor on both trees.

The result is confounded by ECMP. Host 3 shares ToR 0 with congestors 0, 1
and 2, and the victim needs one of ToR 0's 4 uplinks. When its hash lands on
an uplink a congestor also uses, it gets half of that link: 1.96 x floor
(51 Gbps mean, never stalled), on 1:1 seed 1 and 4:1 seed 3 alike. That
is ordinary sharing, not PFC. The PFC victim effect appears once, on 4:1
seed 1: the victim's uplink `LS0->US3` was paused for 6.26 ms because agg 3's
ingress from ToR 0 was full of congestor packets waiting for `US3->CS3`
(utilization 0.9996, the saturated pod uplink). The victim was stalled
(no delivery) in 15% of its 50 us samples and finished at 2.41 x floor,
against about 2.0 for a fair share of that uplink: 0.4 x floor of pure
PFC collateral damage on a flow whose own path had capacity. In seeds 2 and 3
on 4:1 the victim was never stalled (stalled fraction 0): seed 2 it had its
uplink to itself (1.02), seed 3 it shared one with a congestor (1.96), and
the paused ToR 0 uplinks were others. Median over seeds is 1.96 on 4:1 vs 1.02 on
1:1, so the oversubscribed tree hurts the intra-pod victim more, but with 3
seeds the split between ECMP sharing and PFC blocking rests on that one
diagnosed run.

In the load sweeps the same effect is spread across all flows rather than
isolated: on 4:1 load70 the ToR uplinks, which are never the bottleneck,
are paused 45% of their backlogged time.

**Answer for RoCE:** 4:1 binds from the lowest load (every TP = 8 request is
bound at 2 x floor by its pod uplink) and 8:1 at 4 x floor. RoCE adds a
factor of about 2 on top at low load on 1:1 and 4:1 (collisions), less on 8:1
(1.2-1.5), where the single ToR uplink removes the path choice. PFC pauses
idle the bottleneck links themselves for a quarter of their backlogged time
and can stall flows that never touch the oversubscribed link (2.41 vs ~2.0 x
floor in the diagnosed victim run).

## Why (HPCC)

HPCC is the paper-faithful sender of `build_hpccfix` (HTSIM/OUR_CHANGES.md,
"HPCC: from a compounding window to the paper's Algorithm 1"), N = 10,
T = 16.4 us on all three trees (exported by `scripts/explib.sh` for
`fat_tree_128_*` names, see docs/E3.md "HPCC base RTT on ft128"; every log
prints `target RTT 16.4 ... W_AI 1024`), so W_init = B x T = 205,000 B and
W_AI = 1,024 B. Every hop's LosslessOutputQueue stamps INT (queue length,
tx bytes, timestamp, link rate; queue_lossless_output.cpp:186-201) and the
sender reacts to the hop with the largest U (`measureInflightPaper`,
hpcc.cpp:562).

### 1. HPCC does not change what oversubscription costs

At load 30 the oversubscription factor is the same as RoCE's. Interleaved,
p50 goes 2.25 -> 4.41 -> 5.67 x floor from 1:1 to 4:1 to 8:1 (x 1.96 and
x 2.52 of the 1:1 value), against RoCE's 2.12 -> 4.13 -> 5.19 (x 1.95 and
x 2.45). On 4:1 every request is bound by its pod uplink at iso = 2, and
HPCC sits at 2.20 x iso against RoCE's 2.06. The difference is the same
1 / (eta x 9,000 / 9,064) = 1.06 that E3 point 1 measured: HPCC keeps 5% of
every bottleneck free (eta = 0.95, hpcc.cpp:38). The victim alone shows it
directly: 1.055 x floor under HPCC, 1.017 under RoCE, on both trees.
Per seed, HPCC is slower than RoCE on all 9 interleaved load-30 runs (by
4-9%) and on 31 of the 36 load-30 and load-50 runs over both placements.

### 2. On 4:1 at load 70, INT removes RoCE's PFC collapse, and HPCC wins the median

| 4:1 interleaved load70, seed 1 | RoCE | HPCC |
|---|---|---|
| pause share: host NIC / ToR uplink / agg uplink | 0.60 / 0.45 / 0.15 | 0.012 / 0.005 / 0.002 |
| max queue, host NIC (median / max over hosts) | 28,921 / 68,224 pkts of 4 KB | 7 / 14 pkts of 9 KB |
| max queue, agg uplink (median / max) | 320 / 334 pkts of 4 KB | 27 / 36 pkts of 9 KB |
| agg -> core utilization min / median / max (whole run) | 0.10 / 0.44 / 0.82 | 0.07 / 0.34 / 0.67 |
| last flow finishes | 169.2 ms | 197.9 ms |

(`results/e2/diag/{roce,hpcc}_ft128_4os_e2load70_s1_{pfc.md,queues.csv}`,
HPCC decoded with `--pfc-high 15`, HPCC's 15-packet threshold,
main_hpcc.cpp:67.) This is the one cell where RoCE's PFC behaviour was
pathological: its host NICs were paused 60% of their backlogged time and
held up to 68,000 packets each (RoCE point 3). HPCC flows never build a
queue at the NIC, because every source is paced at W / T with W <= W_init
(`setWindow`, hpcc.cpp:603-610) and cuts within an RTT when the INT shows the
agg -> core hop above eta. HPCC's p50 is lower than RoCE's on every seed
(6.58 / 7.72 / 6.04 against 7.92 / 7.86 / 6.48 x floor), and p50 x_ideal is
2.40 against 2.52.

The gain is a redistribution, not more throughput. The per-seed mean
request is 7.20 / 7.47 / 6.76 x floor against RoCE's 8.19 / 7.40 / 6.56, the
worst request 12.12 / 10.98 / 10.98 against 10.87 / 11.26 / 10.02, and the
last flow finishes 20-29 ms later on every seed (197.9 / 180.2 / 164.8 ms
against 169.2 / 160.9 / 144.2). The agg -> core uplinks, the binding
resource, are used less over a longer run (median 0.34 against 0.44). The
requests that lose are long-lived ones: on seed 1 the four flows of request
11 (started at 24.8 ms) finish at 185-187 ms (12.0 x floor; RoCE 129-164 ms)
and request 18's at 197-198 ms (11.5; RoCE 87-142 ms). With 1.41 x
effective load, requests stay active for 100+ ms, so every one of them
meets several later arrivals at the pod uplink. Each newcomer starts at line
rate and the multiplicative cut keeps the ratios (newcomer advantage,
HTSIM/OUR_CHANGES.md "What still differs from an ideal fluid HPCC"), and a
flow that crosses both a busy agg -> core link and a busy downlink sees
max(U_A, U_B) and is held below its max-min share (same section,
"Multi-bottleneck flows lose"). RoCE's per-port FIFO plus PFC moves all
flows of a link at one shared pace, so nobody starves and nobody gets ahead.

### 3. On 8:1, HPCC ties RoCE at the median and loses the tail

8:1 has one 100 G ToR uplink per 4 hosts and 2 core uplinks per agg, so every
cross-pod shard crosses at least two shared links (ToR up at its source, agg
-> ToR at its destination). Interleaved load 70: p50 12.97 against 12.71
(per seed 12.76 / 13.43 / 12.97 against 12.71 / 13.48 / 12.33), x_ideal 1.53
against 1.43. The tail is HPCC's multi-bottleneck squeeze at its clearest:
seed 3's request 11 (6 shards from hosts 48-55 at 24.8 ms) finishes at
310.7-312.9 ms, 21.3-21.5 x floor, against 174-205 ms (11.1-13.4) under RoCE,
and request 4's shards at 20.1 x floor against 9.2-9.7. The run lasts
312.9 ms against RoCE's 237.2. On the split matrices, where pods 0-3 send at
2-4 x effective load, HPCC is slower than RoCE at the median in 10 of 12
seed-cells on 4:1 and 8:1.

### 4. On 1:1, HPCC loses to RoCE when many requests start together

Interleaved load 70 is the largest gap: p50 4.60 against 3.57 (per seed
4.00 / 4.60 / 4.81 against 3.57 / 3.55 / 4.07). The loss is concentrated in
the first eight requests, which arrive within 12.8 ms (four within the first
1.5 ms): per request, HPCC / RoCE completion has a median of 1.40 for those 24
request-seeds and 1.00 for the 39 later ones. The ECMP placement is the same:
both binaries draw one path per flow with `random() % 256` (roce.cpp:66,
hpcc.cpp:81) from the same seed, and at load 30 the uncollided (1x) flows
are the same set in both (28 of 28, 19 of 19, 23 of 23 on seeds 1-3). So the
collisions are the same; what differs is how the collided flows share. Seed 1's request 0 shows it: 6 of its 8
shards finish at 1.06-1.12 x floor in both, but shard 3 -> 27 finishes at
4.07 x floor (54.7 ms) under HPCC against 2.31 (31.0 ms) under RoCE.
The sink samplers of the seed-1 diagnostic runs
(`results/e2/diag/{roce,hpcc}_ft128_1os_e2load70_s1_*`, 1 ms bins) show
how. Under HPCC, 3 -> 27 gets about 41 Gbps for its first 22 ms (RoCE
48). It drops to about 16 Gbps when requests 8-10 arrive at 21.6-22.5 ms
and put flows on its bottleneck (RoCE about 29 Gbps). It then drops to
7-9 Gbps once requests 14 and 15 arrive at 38.1 ms. RoCE's copy of the
flow had already finished at 31.0 ms. Each newcomer starts at
W_init, line rate. The link's U jumps above eta, and every flow on it cuts
by the same factor eta / U (hpcc.cpp:562-574), so the flow that was already
below its share stays below it and only W_AI = 1 KB per RTT moves it back.
RoCE's FIFO egress instead serves every ingress port the same share at once.
PFC is not the cause: HPCC's pause shares in this run are 0.002 (host
NIC), 0.001 (ToR uplink) and 0.001 (agg uplink).

HPCC's own parameter for this is N, the expected number of flows per link
(W_AI = W_init (1 - eta) / N). With N = 2 (`-hpcc_N 2`, W_AI 5,125 B,
`results/e2/hpccN2/`, the only N = 2 load level in this document), p50 is
3.33 / 3.54 / 3.93 on seeds 1-3. That compares with 4.00 / 4.60 / 4.81 at
N = 10 and RoCE's 3.57 / 3.55 / 4.07. p99 is 5.07 / 5.14 / 6.35, against
5.90 / 6.60 / 7.41 at N = 10 and RoCE's 5.58 / 5.69 / 7.90. A five times
larger additive step lets the squeezed incumbents climb back within a few
RTTs, which closes the gap. As in E3, this is a sensitivity point, and the
tables report N = 10.

### 5. The victim test: HPCC gives the victim what the congestor cannot use

| run | victim 3 -> 15 | congestor sharing its ToR uplink | PFC on the victim's uplink |
|---|---|---|---|
| RoCE 4:1 seed 1 | 2.41 | 2 -> 66 at 2.45 | 6.26 ms paused, victim stalled 15% of its samples |
| HPCC 4:1 seed 1 | 1.22 | one congestor, itself bottlenecked at an agg -> core link | 0.03 ms paused (`LS0->US1`) |
| HPCC 4:1 seed 3, 1:1 seed 1 | 2.08 | a congestor with no tighter bottleneck | none |

HPCC's victim is 1.06 on 3 of 6 seed-runs (alone on its uplink: the eta
factor), 2.08 on two (a fair half of an uplink shared with a congestor, like
RoCE's 1.96 cases) and 1.22 on 4:1 seed 1, the run where RoCE's victim was
hit by PFC. There ToR 0's four flows (congestors 0, 1, 2 and the victim) use
two uplinks, `LS0->US1` and `LS0->US3`, two flows each (27.0 ms of service
each, 13.4 ms per flow). The victim's 1.22 means it averaged 82 Gbps on a
shared uplink, so the congestor beside it was held to under 20 Gbps by its
own bottleneck further up: the pod's agg -> core uplinks, where `US3->CS3`
carries three congestors at 0.90 utilization. HPCC reacts to the max-U hop
of each flow, so the victim, whose worst hop is the uplink, takes what the
congestor cannot use instead of half the link, and no ingress fills to pause
it (max queue at `LS0->US1` 23 packets of 9 KB, 0.03 ms paused;
`results/e2/diag/hpcc_ft128_4os_victim_s{1,3}_*`).
That is max-min sharing; RoCE gave 2.41 because the uplink was split per
ingress port and then paused for congestor traffic.

**Answer for HPCC:** HPCC does not make oversubscription cheaper (4:1 and
8:1 cost x 1.96 and x 2.52 at load 30, as under RoCE) and pays its 5%
headroom everywhere. It removes PFC (pause share <= 0.012 where RoCE had
0.60) and protects the victim, which wins the median on 4:1 at 1.41 x
effective load. But its fairness is weaker than RoCE's FIFO under
long-lived overlap: newcomers and single-bottleneck flows get ahead of
flows crossing two busy links, so the worst request and the last finish get
worse on 4:1 and 8:1, and on 1:1 a burst of simultaneous arrivals costs 40%.

## Why (EQDS)

EQDS is `build_eqds2`, the same binary as E3. Its mechanisms are listed in
docs/E3.md "Why (EQDS)": per-packet spraying over 16 entropies
(`nextEntropy`, eqds.cpp:1238), one receiver pull pacer per host at
0.99 x linkspeed (main_eqds.cpp:550), and COMPOSITE queues
(main_eqds.cpp:57) that trim instead of pausing. When a queue's 2,000
packets are full, a payload is cut to a 64 B header (`trimsize`,
main_eqds.cpp:52; compositequeue.cpp:189-211) that jumps the queue. The
sink NACKs it, and the retransmission is pulled first (`_rtx_senders`,
eqds.cpp:2253). `run.sh` does not pass `-sender_cc` (main_eqds.cpp:156), so
this is EQDS without sender-side congestion control. Every run completed
with 0 stale NACKs and 0 bounces, and 0-4 RTS per run.

### 1. Spraying removes the transport's share of the cost, so oversubscription shows its full price

| matrix | 1:1 | 4:1 | 8:1 | RoCE x_ideal (1:1 / 4:1 / 8:1) |
|---|---|---|---|---|
| interleaved load30, p50 (x_ideal) | 1.14 (1.14) | 2.22 (1.11) | 4.54 (1.12) | 2.12 / 2.06 / 1.30 |
| interleaved load50 | 1.15 (1.15) | 2.69 (1.19) | 7.60 (1.23) | 3.05 / 2.56 / 1.46 |
| interleaved load70 | 1.16 (1.15) | 3.68 (1.23) | 11.55 (1.28) | 3.51 / 2.52 / 1.43 |
| split load30 | 1.26 (1.26) | 3.97 (1.08) | 8.86 (1.13) | 3.04 / 1.55 / 1.18 |
| split load50 | 1.31 (1.31) | 6.50 (1.11) | 16.12 (1.17) | 4.05 / 1.44 / 1.18 |

EQDS is within 8-31% of the ideal fabric in every cell. RoCE, HPCC and
DCQCN are 2-5x off on 1:1 and 4:1. With the transport's waste gone, the
ratio between trees is the oversubscription itself: at interleaved load 30,
p50 goes 1.14 -> 2.22 -> 4.54 (x 1.95 and x 3.98), against iso bounds of
2 and 4. RoCE's 2.12 -> 4.13 -> 5.19 (x 1.95 and x 2.45) looks cheaper on
8:1 only because RoCE already wastes a factor of 2 on 1:1. In absolute
terms EQDS is still best everywhere. The margin over RoCE shrinks with
oversubscription: 1.86-3.08x faster on 1:1, 1.38-2.14x on 4:1 and
1.02-1.14x on 8:1 (p50, all matrices). As E2's RoCE point 2 explained, on
8:1 a ToR has one uplink, so there is little path choice left for spraying
to improve on.

### 2. The receiver credits its own link, so retransmissions grow with oversubscription

| matrix | 1:1 | 4:1 | 8:1 |
|---|---|---|---|
| interleaved load30 | 3.2-4.8% | 46-50% | 74-77% |
| interleaved load50 | 3.8-4.9% | 51-55% | 102-155% |
| interleaved load70 | 3.8-4.4% | 66-70% | 130-176% |
| split load30 | 3.3-5.6% (E3) | 193-196% | 540-557% |
| split load50 | 3.1-4.4% (E3) | 247-250% | 659-673% |

(Rtx / new packets, seeds 1-3, from each summary's `log_counters`.) The
pull pacer sizes credit to the receiver's own 100 G downlink. It cannot
see that a cross-pod shard on 4:1 can get only about 50 G (iso = 2), and on
8:1 about 25 G. Credit therefore lets senders put about twice (4:1) or four
times (8:1) the bottleneck's share into the network, and the excess is
trimmed at the oversubscribed hop. The queue samplers show where
(`results/e2/diag/eqds_*`, seed 1, finish times and Rtx identical to the
sweep runs; the sampler window runs to END, so times are absolute):

- 4:1 interleaved load70 (run lasts 102.5 ms): all 32 agg -> core uplinks
  reach the 2,000-packet trim point. The median one sits there for 28 ms
  and the worst for 40 ms. Core downlinks spend 3 ms there (median; worst
  15 ms), and ToR uplinks 0 (worst 7 ms). The receivers' ToR downlinks peak
  at 723 packets and never trim.
- 8:1 split load30 (184.4 ms): all 16 active ToR uplinks and all 8 active
  agg uplinks reach 2,000 packets, for a median of 62 and 60 ms. Agg
  downlinks peak at 984 packets, and core downlinks hold 1.

A trim costs the bottleneck 64 B instead of a 4,150 B packet, so the
bottleneck keeps forwarding payload almost all the time. The extra copies
cost bandwidth on the hops before it (host NIC, and the ToR uplink on 4:1),
which have room. That is why EQDS stays close to the ideal while it sends
each byte up to 7.7 times. The cost shows elsewhere. First, a tail on 8:1
at low load: interleaved load30 has p99 8.25 (x_ideal 1.55) and Jain 0.940,
against 0.98-1.00 everywhere else. Second, simulation time: the 8:1
interleaved load70 runs took 805-1,010 s, against RoCE's 52 s. Sender-side
CC (`-sender_cc`) exists for exactly this in-network congestion. This
document does not run it.

### 3. No PFC, so no victim

| run | victim 3 -> 15 x_floor (seeds 1 / 2 / 3) | congestors, median / max | ideal for the congestors |
|---|---|---|---|
| 1:1 | 1.07 / 1.06 / 1.17 | 1.09 / 1.12 | 1.0 |
| 4:1 | 1.05 / 1.06 / 1.18 | 1.52 / 1.57 | 1.5 (600 G through 400 G) |
| victim alone | 1.03 | - | - |

Trimming drops payload at the congested queue instead of pausing the port
upstream, so nothing stops the victim's hops. Spraying also spreads the
victim over all four of ToR 0's uplinks, so it never gets the half-link
that RoCE, HPCC and DCQCN give it when its hash matches a congestor's.
On 4:1 seed 1 (`results/e2/diag/eqds_ft128_4os_victim_s1_*`) the four agg
-> core uplinks of pod 0 reach 2,000 packets for 1-1.9 ms. ToR 0's
uplinks peak at 8 packets (median), and one reaches 2,000 briefly. The
congestors themselves finish at 1.52-1.63 x floor, against the 1.5 that
the pod's 400 G of uplink allows. RoCE's congestors finish at 2.03-3.05.
Seed 3's 1.17-1.18 on both trees is the hash imbalance of 16 entropies on
ToR 0's uplinks, which its packets share with congestors 0-2.

**Answer for EQDS:** EQDS removes almost all of the transport's own cost
(x_ideal 1.08-1.31 in every cell, against 1.2-4.5 for the pinned-path
transports). So it is the only policy for which E2 measures the
oversubscription itself: x 1.95 on 4:1 and x 3.98 on 8:1 at load 30, close
to the iso bounds of 2 and 4. It pays for this with retransmissions. Its
credit is sized to the receiver link, so the oversubscribed hop trims 46-70%
(4:1) and 74-673% (8:1) of the new packets. That costs little goodput,
because trims are headers. It also removes the PFC victim (1.05-1.18).

## Why (DCQCN)

DCQCN is the binary and flags of docs/E3.md "Why (DCQCN)": `build` at
commit 4d3e1b2 (paper reaction point, RED marking with `-ecn_kmin 12
-ecn_kmax 400 -ecn_pmax 0.01` at 100 G, minimum-rate clamp at
R_AI = 0.1 Gbps), with PFC underneath. That section lists the mechanism
with file:line references. The sweep was first run without the clamp
(`results/e2/dcqcn_preclamp/`). The clamp changed 37 of the 51 runs, by
-7% to +6% at the p50, and it made the one invalid pre-clamp run complete
(point 4). CNP counts come from `DCQCN_TRACE=1` reruns of every DCQCN E2
run, each identical to its sweep run.

### 1. The startup collapse costs a fixed time, so it matters less the more oversubscribed the tree

The mechanism is E3's. Every collided flow is cut by one CNP per 50 us at
alpha = 1, then recovers at R_AI = 100 Mbps per 55 us. At load 30 (seed 1
trace) 65 of 72 flows are cut in their first 300 us, to a median of
3.1 Gbps. The 2x-5x x_floor classes need a median of 9.5-13.5 ms to
reach 90% of their share. That is the same ~10 ms as on 1:1 (docs/E3.md
point 2). But the flows on 4:1 live 30-90 ms, because every request is
bound at 2 x floor by the pod uplink. A fixed recovery is a smaller part of
a longer transfer, and the share it has to climb back to is half as high.
DCQCN / RoCE p50 per seed, interleaved load 30:

| tree | DCQCN / RoCE (seeds 1 / 2 / 3) | DCQCN p50 x_iso | RoCE p50 x_iso |
|---|---|---|---|
| 1:1 | 1.19 / 1.37 / 1.46 | 3.09 | 2.12 |
| 4:1 | 1.16 / 1.16 / 1.18 | 2.39 | 2.06 |
| 8:1 | 1.09 / 1.12 / 1.12 | 1.46 | 1.30 |

So DCQCN, too, makes oversubscription look cheaper than it is, as RoCE
does: p50 goes 3.09 -> 4.78 -> 5.83 (x 1.55 and x 1.89 of 1:1). That is
because its 1:1 baseline is worse, not because it handles the
oversubscribed link better.

### 2. On 4:1 at load 70, removing PFC wins the median, as with HPCC

| 4:1 interleaved load70, seed 1 | RoCE | DCQCN |
|---|---|---|
| pause share: host NIC / ToR uplink / agg uplink | 0.60 / 0.45 / 0.15 | 0.002 / 0.005 / 0.004 |
| max queue, host NIC (median / max over hosts) | 28,921 / 68,224 pkts | 40 / 2,887 pkts |
| agg -> core utilization min / median / max (whole run) | 0.10 / 0.44 / 0.82 | 0.10 / 0.44 / 0.85 |
| last flow finishes | 169.2 ms | 161.0 ms |

(`results/e2/diag/{roce,dcqcn}_ft128_4os_e2load70_s1_*`.) DCQCN uses the
binding agg -> core uplinks exactly as much as RoCE. What changes is that
RoCE's host NICs, paused 60% of their backlogged time, held tens of
thousands of packets that waited on the slowest path any of them used.
DCQCN's NICs barely queue (median 40 packets), because the sources are
paced at R_C (roce.h:48).
It reacts to marks at Kmax = 400 KB, below the 600 KB XOFF. The p50 is
lower on seeds 1 and 2 (7.36 / 7.21 against 7.92 / 7.86) and higher on
seed 3 (7.11 against 6.48). The median over seeds is 7.21 against 7.86
(x_ideal 2.44 against 2.52; HPCC 2.40). Worst requests are 9.86 / 9.76 /
11.43 against 10.87 / 11.26 / 10.02. At 1.41 x effective load the
collapse is cheap next to RoCE's PFC collapse. It is not free: 37-58 of the
168 flows per seed are cut all the way to the clamp.

### 3. On 8:1, DCQCN ties RoCE

Interleaved load 70: p50 12.86 against 12.71 (per seed 13.33 / 12.86 /
12.63 against 12.71 / 13.48 / 12.33), x_ideal 1.47 against 1.43.

| 8:1 interleaved load70, seed 1 | RoCE | DCQCN |
|---|---|---|
| ToR uplink (the bottleneck) utilization min / median / max | 0.46 / 0.68 / 0.69 | 0.45 / 0.66 / 0.67 |
| ToR uplink above XOFF (median / max over queues) | 83% / 99% of samples | 0.5% / 0.7% |
| host NIC max queue (median) | 56,458 pkts | 24 pkts |
| pause share: host NIC / ToR uplink / agg uplink | 0.80 / 0.28 / 0.12 | 0.004 / 0.004 / 0.004 |

(`results/e2/diag/{roce,dcqcn}_ft128_8os_e2load70_s1_*`.) On 8:1 the 4
hosts of a ToR share its single uplink whatever the hash, so the
bottleneck is unavoidable for both. RoCE keeps it busy by queueing
everything and pausing upstream. DCQCN keeps it about as busy by
cutting. Here the cuts are severe: 97-112 of the 168 flows per seed reach
the clamp. The two balance: same utilization, same median, and DCQCN's
worst request is no better (15.97 / 18.15 / 17.57 against 16.15 / 15.16 /
15.14).

### 4. Before the clamp, deep cuts silenced flows, and one never finished

Without the clamp R_C has no floor (dcqcn.cpp:85 before 4d3e1b2). RoceSrc
books its next send at `_time_last_sent + _packet_spacing` when it sends
(roce.cpp:340-343), and a rate increase only recomputes the spacing
(dcqcn.cpp:148-149). A flow cut to near zero therefore stayed silent for
its whole last gap, unless a PFC RESUME (roce.cpp:229) woke it.

- **The invalid pre-clamp run, 4:1 interleaved load50 seed 2.** Flow 37 ->
  77 (request 10, shard 5, start 38.1 ms) got 59 CNPs from 46.9 to 49.8 ms,
  one per 50 us, which took R_C from 73 Gbps to 1.4 x 10^-7 Gbps (140 bps).
  Its last packet booked the next send about 230 s later. The trace shows R_C
  climbing back to 100 Gbps, but the byte counter stays at 0 and no packet
  leaves, because nothing pauses that source and so nothing wakes it. The
  run is INCOMPLETE even with END = 3.2 s, 119 of 120 flows
  (`results/e2/dcqcn_preclamp/dcqcn_fat_tree_128_4os_e2load50_r2_s2_summary.incomplete.json`).
  It was left out of the pre-clamp table. With the clamp it completes:
  p50 6.14, 120 of 120 flows.
- **Silences on 8:1 load70 (seed 3).** The pre-clamp queue sampler
  (`results/e2/diag/preclamp/dcqcn_ft128_8os_e2load70_s3_*`) shows the
  longest zero-delivery stretch per flow at a median of 0.53 ms. 70 flows
  exceed 1 ms, 8 exceed 5 ms and 6 exceed 10 ms. Flow 16 -> 72 delivered
  nothing from 44 to 68 ms, and the slowest flow, 53 -> 93, had a 10.6 ms
  silence. With the clamp the gap at the floor is (4,000 + 64) B x 8 /
  0.1 Gbps = 325 us. In the same run the longest silence is 0.30 ms (median
  0.25 ms), and the stalled fraction drops from a maximum of 0.151 to 0.009
  (`results/e2/diag/dcqcn_ft128_8os_e2load70_s3_*`).

The clamp therefore matters most on the oversubscribed trees, where most
flows reach it. The median moves by only a few percent, because a silent
flow's share was taken by the other flows on its bottleneck. The pacing
problem itself is still there: a rate increase still does not move a
booked send. The clamp only bounds the gap at 325 us at 100 G and 81 us at
400 G.

### 5. The victim test: no PFC victim, but the collapse hits the victim when it shares a link

| run | victim 3 -> 15 | what it shares | pause on its path |
|---|---|---|---|
| 1:1 seeds 2, 3 / 4:1 seed 2 | 1.02 | nothing (an uplink to itself) | none |
| 4:1 seed 1 | 1.51 (66 G mean) | ToR uplink with congestor 2 -> 66, which is held to 28 G by `US3->CS3` (0.82 utilization) | 0.04 ms (`LS0->US3`), victim never stalled |
| 1:1 seed 1 | 2.55 (39 G mean) | `LS0->US1` (0.78 utilization) with congestor 1 -> 65 | none |
| 4:1 seed 3 | 2.36 | a ToR uplink with a congestor | none |

(`results/e2/diag/dcqcn_ft128_{1os,4os}_victim_s1_*` and seed-1 traces.)
On 4:1 seed 1, the run where RoCE's victim was paused for 6.26 ms and
finished at 2.41, DCQCN's victim finishes at 1.51. Marks stop the
congestors before their ingress counters reach XOFF, so the uplink is not
paused for them. The victim takes what the congestor beside it cannot use,
as under HPCC (1.22). Three congestors share `US3->CS3` and were cut to
1.6-3.1 Gbps at startup.

DCQCN loses to RoCE's 1.96 when the victim simply shares an uplink with a
congestor that has no tighter bottleneck. On 1:1 seed 1 the victim's start
at 1 ms pushes that uplink's queue over Kmax. Both flows get 3 CNPs within
100 us (first at 1,041 and 1,044 us), and both drop to 12.5-15.2 Gbps.
The victim then climbs back at 1.8 Gbps/ms while competing with an
incumbent, finishing at 2.55 x floor against a fair half's 2.0. That is
E3's collision collapse applied to the victim, not PFC: pause share is
<= 0.001 in every class. The congestors finish at 2.38 / 3.72 (median /
max) on 4:1, against RoCE's 2.03 / 3.05.

**Answer for DCQCN:** DCQCN does not change what oversubscription costs.
Its ~10 ms startup penalty is a fixed cost, so it is +19-46% over RoCE on
1:1 at load 30 and +9-12% on 8:1. Removing PFC pays where RoCE's PFC
collapsed: 4:1 at load 70, median 7.21 against 7.86, and the PFC victim
(1.51 against 2.41). On 8:1 it ties RoCE. The cuts there are so deep that
most flows reach the minimum rate. Before the clamp this stalled flows for
up to 24 ms and left one flow unfinished.

## Comparison across policies (E2)

| | RoCE | HPCC (N = 10) | DCQCN | EQDS |
|---|---|---|---|---|
| interleaved load30 p50, 1:1 / 4:1 / 8:1 | 2.12 / 4.13 / 5.19 | 2.25 / 4.41 / 5.67 | 3.09 / 4.78 / 5.83 | 1.14 / 2.22 / 4.54 |
| interleaved load70 p50, 1:1 / 4:1 / 8:1 | 3.57 / 7.86 / 12.71 | 4.60 / 6.58 / 12.97 | 4.58 / 7.21 / 12.86 | 1.16 / 3.68 / 11.55 |
| p50 x_ideal, all 15 cells | 1.18-4.05 | 1.21-4.13 | 1.18-4.51 | 1.08-1.31 |
| oversubscription cost at load30, 4:1 / 8:1 over 1:1 | x 1.95 / x 2.45 | x 1.96 / x 2.52 | x 1.55 / x 1.89 | x 1.95 / x 3.98 |
| host NIC pause share, 4:1 load70 seed 1 | 0.60 | 0.012 | 0.002 | no PFC |
| victim 3 -> 15, median (1:1 / 4:1) | 1.02 / 1.96 | 1.06 / 1.22 | 1.02 / 1.51 | 1.07 / 1.06 |
| loss recovery | none (PFC) | none | none | 3-5% (1:1) to 673% (8:1 split) of new packets retransmitted |
| wall time per run | 20-148 s | 6-54 s | 13-43 s | 26-1,010 s |

The pinned-path transports (RoCE, HPCC, DCQCN) are 1.2-4.5x slower than
the ideal fabric. Most of that is ECMP collisions, and their congestion
control changes it by tens of percent. HPCC and DCQCN remove PFC. That wins
the median only where PFC collapsed, on 4:1 at 1.41 x effective load. It
costs them elsewhere: HPCC its 5% headroom and newcomer squeeze, DCQCN its
startup collapse. EQDS's spraying removes the collisions, so it is within
8-31% of the ideal everywhere. It is the one policy whose numbers show
what the oversubscription itself costs, close to the iso bounds of 2x and
4x. On 8:1, where every transport is bound by the same single ToR uplink,
its lead over RoCE shrinks to 2-13%, and on split load30 it is 3% behind
(8.86 against 8.59 x floor).
