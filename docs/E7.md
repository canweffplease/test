# E7: scale-up domain size, or how much of the problem hardware removes on its own

**Question.** If the scale-up domain (GPUs sharing NVLink/NVSwitch) holds 8
GPUs (one HGX node) or 72 (one NVL72 rack), what fraction of prefill->decode
KV cache transfers, and of KV bytes, never touches the Ethernet fabric? What
does that do to the offered load at each fabric tier?

**Short answer.** The domain size does almost nothing on its own. **Placement
decides the outcome.** With domain-oblivious (random) placement the fraction
of bytes on the fabric is about `1 - D/H`: 100 % at D=8 and 93.8 % at D=72
on a 1,152-GPU cluster. The bigger domain removes only 6 % of the bytes, and
92 % still cross the pod uplinks. With locality-aware placement (prefer a
decode instance in the same domain) the picture flips:

| 1,152 GPUs, Llama-3-70B, prefill:decode 1:2 | D = 8, TP = 8 | D = 72, TP = 8 | D = 8, TP = 4 | D = 72, TP = 4 |
|---|---|---|---|---|
| random | 1.000 | 0.938 | 0.995 | 0.938 |
| rail-aligned | 1.000 (0 cross-pod) | 0.938 (0 cross-pod) | 1.000 (0 cross-pod) | 0.938 (0 cross-pod) |
| locality-aware, unconstrained decode capacity | **1.000** | **0.000** | **0.000** | **0.000** |
| locality-aware, c = 16 slots per decode instance, 80 % utilization (MC, 95 % CI) | **1.000 +/- 0.000** | **0.006 +/- 0.001** | **0.577 +/- 0.005** | **0.000 +/- 0.000** |

Entries are the fraction of KV bytes on the fabric (`results/e7/e7_closedform.csv`,
`results/e7/e7_mc.csv`, set `headline`).

- **D = 8, TP = 8.** One HGX node holds exactly one TP=8 instance, so a node
  is either prefill or decode. Every disaggregated transfer crosses the
  fabric whatever the placement policy, and about 95 % of the bytes cross
  the core. This is the Splitwise and Mooncake deployment shape, with
  separate prefill and decode machine pools, and it is the case this project
  simulates.
- **D = 72, TP = 8.** A rack holds 9 instances. At 1:2 that is 3 prefill and
  6 decode per rack, which is exactly the global ratio. Locality-aware
  placement keeps 99.4 % of the bytes on NVLink at 80 % decode utilization.
  It still keeps 80 % at 95 % utilization (with c = 16). The fabric only
  sees the spill.
- **D = 8, TP = 4.** A node holds two instances, so it can be one prefill
  plus one decode. With unconstrained capacity that looks perfect (0 %). But
  at 1:2 each prefill instance's output needs two decode instances' worth of
  capacity and its node has one. Under realistic capacity, 58 % of the bytes
  still leave the node.

**Rule of thumb.** Locality removes the fabric transfer when one domain can
hold a *balanced* set of instances, that is, when the number of instances
per domain (D/TP) is a multiple of p+d for a prefill:decode ratio of p:d.
Otherwise the fabric carries the imbalance (table in section 4). A bigger
domain helps because it makes that balance possible, not because it holds
more GPUs.

**What E7 tells the rest of the project.** The transfers our HTSIM
experiments study (prefill and decode in different scale-up domains, TP=8 on
8-GPU nodes) are *all* of the KV traffic in the HGX-class deployments
described by Splitwise and Mooncake. They are *all but about 6 %* of it on
NVL72 hardware if the scheduler ignores locality. They shrink to a spill of
0-20 % (depending on utilization and ratio) only if the deployment both
co-locates the roles inside a rack and places by locality. So the
cross-fabric transfer remains the default case. NVL72 turns it into a
placement choice, not something the hardware eliminates.

**Limitation.** This is a placement/locality calculation, not a transport
result. It counts which bytes must cross which tier and what average load
that implies. It says nothing about how long those transfers take; that is
what E1-E6 measure. The project's scope is the transfers that cross the
fabric, and E7 says how many those are.

## 1. Model

Everything is computed by `scripts/e7_scaleup.py` (stdlib + numpy, matplotlib
for the figures). It imports `Topo`, `get_topo` and `parse_ts` from
`scripts/gen_workload.py`, so the fat-tree host->ToR->pod mapping is the
generator's.

### Cluster, domains, instances

| symbol | meaning | values |
|---|---|---|
| H | GPUs = fat-tree hosts (one GPU, one NIC, as in the generator) | 128, 1,024, 1,152 |
| D | scale-up domain: D consecutive GPU ids share an NVSwitch | 8 (HGX), 72 (NVL72); figure sweeps 8-576 |
| TP | GPUs per prefill or decode instance (consecutive ids) | 4, 8 |
| p:d | prefill : decode instances | 2:1, 1:1, 1:2, 1:3 |
| c | concurrent requests one decode instance accepts | inf, 4, 16, 64 |
| rho | mean fraction of decode slots occupied | 0.5, 0.8, 0.95 |

- **Domains** are GPUs `[kD, (k+1)D)`. Instances are packed from the start
  of each domain and **never straddle a domain**, because TP needs NVLink.
  Leftover GPUs idle (D=36, TP=8 leaves 4 per domain).
- **72 does not divide 128 or 1,024.** Three clusters are reported:
  - **ft128** (`fat_tree_128_{1,4}os`, 4 hosts/ToR, 16 hosts/pod, 100 G):
    D=72 is one full rack plus one 56-GPU partial domain.
  - **ft1024** (`fat_tree_1024_{1,4}os`, 8 hosts/ToR, 64 hosts/pod, 200 G):
    D=72 is 14 racks plus a 16-GPU partial domain.
  - **ft1152** (synthetic): the 1024 files extended to 18 pods with the
    same per-ToR and per-pod capacities. It holds exactly 16 NVL72 racks or
    144 HGX nodes. It is the headline cluster and the figure's cluster. A
    radix-16 core cannot actually wire 18 pods, so this is an accounting
    device, not a buildable `.topo`.

  A partial domain is treated as a smaller scale-up domain, like a partially
  populated rack.
- **GPU g is fat-tree host g**, the generator's labelling. NVL72 racks are
  therefore not aligned to pods (a 72-GPU rack spans 1.125 pods of 64). Only
  the tier split of the *fabric* bytes depends on this, not the off-fabric
  fraction.

### Role layout: which instance slots are prefill

- **mixed** (default): a Bresenham spread. Every run of p+d consecutive
  slots has exactly p prefill, so each domain holds both roles as close to
  the global ratio as its instance count allows. This is the deliberate
  deployment that locality needs, and the best case for it.
- **pooled**: the first p/(p+d) of the slots are prefill. This is
  `gen_workload.py --placement split`, the Splitwise/Mooncake shape. The
  pools meet only in the boundary domain.
- **shuffled**: the mixed multiset in random order (20 random layouts, mean
  and 95 % CI).

### Placement policies (which decode instance gets a request)

The prefill instance is uniform at random, which assumes a load-balanced
front end. Then:

| policy | rule | wiring it is scored on |
|---|---|---|
| (a) random | uniform over decode instances | conventional fat tree |
| (b) locality-aware | uniform over decode instances **in the same domain** that have a free slot; else uniform over free ones anywhere | conventional fat tree |
| (c) rail-aligned | uniform over decode instances whose every shard i lands on the **same rail** as prefill shard i (same local GPU offsets); else anywhere | rail-optimized labelling |
| (d) locality + rail | same domain, else same rail, else anywhere | rail-optimized labelling |

**Rail-optimized labelling.** This is `gen_workload.py --placement rail`
(and `rail_128_1os.topo`) generalized. Local GPU j of every domain sits on
rail `j mod 8`, and each rail is one pod-like group. A matched-index shard
therefore never crosses the core, and a mismatched one always does. On ft128
this is exactly the generator's rail placement (rail = pod of 16). On
1024/1152 each rail is a group of 128/144 hosts. It is scored as one pod
whose ToRs hold 8 consecutive rail members, with the base tree's per-host
uplink capacity. A real rail leaf would be a single switch, so on the 4:1
tree, whose 1024 file oversubscribes the ToR tier, this mapping
*understates* the rail fabric.

**Capacity.** Decode instance d holds a request for its decode time. When
all c slots are busy the instance is skipped. If every decode instance in
the cluster is full, the request goes over capacity to a random one,
counted as `overflow` in `e7_mc.csv`. This models no queueing. Overflow is
below 0.06 % at rho <= 0.8, except the code trace with c = 4 (0.9-3.9 %).
At rho = 0.95 it reaches up to 13 %, mostly with small c and the code
trace's long output tail. **The rho = 0.95 numbers therefore
include global saturation** (the cluster is momentarily full, so the spill
goes anywhere), not just loss of locality.

### Bytes and flows

Llama-3-70B is 327,680 B/token (320 KiB). A request of P prompt tokens at
TP=T is T flows of `ceil(P x 327,680 / T)` B, prefill GPU i -> decode GPU i,
as in the generator. Fractions are byte-weighted. An intra-domain transfer
is assumed to move entirely over NVLink. It never touches a NIC, ToR or pod
uplink, so it is invisible to the Ethernet fabric. NVLink bandwidth is not
modelled, since it is out of the project's scope.

**Transfer fraction = byte fraction** whenever placement ignores prompt
length, which all four policies do. Prompts then change the absolute Gbps,
never the fractions. The MC confirms this: transfer and byte fractions agree
within the CI (`tx_fabric` vs `bytes_fabric` in `e7_mc.csv`).

### Tiers

For each shard, the tier it crosses is:

- NVLink if source and destination share a domain;
- same ToR (`tor`);
- same pod (`agg`), which crosses the ToR uplinks;
- cross-pod (`core`), which crosses the pod's agg->core uplinks.

### Closed form (c = inf)

For prefill instance p, the policy is a probability vector over decode
instances: uniform over the first non-empty preference set. Every fraction
is an exact expectation, `W[p,d] = (1/P) q_p(d)`. For the random policy and
the mixed layout this reduces to

    fabric fraction = 1 - (decode instances in your domain) / (all decode instances)  ~  1 - D/H

So D=72 on H=1,152 gives 1 - 6/96 = 0.9375, and D=576 gives 0.5.

**Fluid bound (c large, utilization rho).** A domain with nP prefill and nD
decode instances receives nP/P of the requests. That is a decode occupancy
of `rho x Dn x nP/P` instances' worth, of which at most nD can stay local:

    fabric fraction >= 1 - sum over domains of (nP/P) x min(1, nD x P / (rho x Dn x nP))

Example: D=8, TP=4, 1:2, rho=0.8. A node holding one P and one D needs
0.8 x 2 = 1.6 decode instances' worth of capacity and has 1, so at least
0.375 of the bytes must leave. This is printed as `fluid` in the tables.

### Monte Carlo (c finite)

This is an event simulation of slot occupancy. The cluster at utilization
rho needs `rho x Dn x c / E[hold]` requests/s. One Azure trace offers only
5.5 req/s (conv) or 2.6 req/s (code). So the workload is the
**superposition of K independent copies** of the trace (each started at a
uniformly random offset into the hour, circular), with

    K = rho x Dn x c / (trace rate x E[hold])

Non-integer K is handled by thinning. Each request keeps its own prompt
length, output length and the trace's arrival structure. The decode hold
time is `GeneratedTokens x TPOT` with **TPOT = 50 ms (assumption)**. The
fixed-4K workload uses Poisson arrivals, exponential holds (mean 1 s) and
4,096-token prompts.

The measurement window is 40 mean hold times after an 8-hold warm-up, which
is 7.5k-470k requests per run. Each point has 10 seeds, reported as mean and
95 % t-interval.

Checks printed by the script:

- With c = inf the MC agrees with the closed form at every point (0
  deviation beyond the CI).
- For D=8, TP=4, 1:1 (one local decode instance of 16 slots per node,
  rho = 0.8) the MC spill is 0.146, against an isolated-node Erlang-B of
  B(12.8, 16) = 0.081. Erlang-B is a lower bound because spilled-in
  requests from other nodes also occupy local slots.

### Offered load and headroom

**Native rate** is the trace's own mean (README, "Azure LLM inference
trace"): conv 5.53 req/s and 16.7 Gbps of KV, code 2.57 req/s and 13.8 Gbps.
"fixed4k" is the conv arrival times with 4,096-token prompts: 59.4 Gbps.

The per-tier Gbps is that rate times the tier fractions. The **headroom
multiplier** uses the generator's bottleneck model (perfect balancing inside
each link group):

    k = min over resources r of capacity(r) / (native KV rate x share(r))

Three numbers come out:

- **k_core** is restricted to the pod agg->core up/down groups: how many
  times the request rate can grow before the cross-pod uplinks saturate.
- **k_any** covers NICs, ToR uplink groups and pod uplink groups.
- **max req/s** is `k_any x native req/s`.

### Assumptions not taken from any paper

- All of the following are assumptions: prefill:decode ratios, the mixed
  layout, uniform prefill choice, c, rho, TPOT, 8 rails, and identity
  host labelling.
- KV is moved once, after prefill. There is no layer-wise streaming, which
  would change timing but not bytes or tiers.
- One NIC per GPU.
- No prefix-cache reuse, which would change bytes, and caching is out of
  scope.
- GPU compute limits are not modelled.

## 3. Why

1. **A domain of one instance cannot help.** With D = TP (HGX, TP=8) a domain
   is a single instance, so it is either prefill or decode, never both. Every
   disaggregated KV transfer must leave the node, regardless of policy,
   capacity, ratio or layout (all D=8/TP=8 rows are exactly 1.000). The only
   network choice left is which tier carries the bytes. Rail-aligned
   placement on rail wiring keeps all of them off the core.
2. **Random placement scales with D/H, not D.** The chance that a random
   decode instance happens to be in your domain is the domain's share of
   decode instances, about D/H. Going from 8 to 72 GPUs moves that from
   0-0.5 % to 6.3 % on 1,152 GPUs. The fabric still carries 94 % of the bytes
   and the core 92 %.
3. **Locality needs the roles co-located.** In the pooled layout (separate
   prefill and decode racks, as in Splitwise and Mooncake), locality-aware
   placement at D=72 still leaves 94-100 % on the fabric, because only the
   boundary rack contains both roles (table in section 5). The off-fabric
   gain at D=72 comes from *deploying* both roles in each rack, a scheduler
   and cluster-manager decision.
4. **Capacity balance decides the residual.** A domain with nP prefill and
   nD decode instances can absorb its own prefill output only if
   nD/nP >= rho x Dn/P, the global decode-per-prefill ratio scaled by
   utilization. With D=72, TP=8 there are 9 instances per rack, which splits
   exactly at 1:2 (3+6). At 1:1 and 1:3 it cannot (4+5 or 5+4; 2+7 or
   3+6), and the fabric carries 6.7-7.0 % of the bytes at c=16, rho=0.8.
   With D=8, TP=4 a node holds 1+1, which balances only 1:1. At 1:2 and 1:3
   the fluid bound is already 0.375 and 0.583. The MC is worse, 0.577 and
   0.692, because random spills from other nodes also land on a node's local
   decode instance and displace its own prefill's requests. A spill policy
   that sends overflow preferentially to decode instances *without* a local
   prefill would approach the fluid bound. We did not model it.
5. **Rail alignment and NVLink locality do different things.** Rail
   alignment never removes bytes from the fabric. It only stops them from
   crossing the core. NVLink locality removes bytes entirely. Combined, the
   spill from locality-aware placement lands on a rail instead of the core
   (locality + rail rows: same fabric fraction; cross-pod at most 1 % at
   rho <= 0.8, at most 11 % at rho = 0.95 with c = 4, which is the global
   overflow above).

**Ratio and packing.** Locality-aware, c=16, rho=0.8, conv, ft1152, mixed
(`e7_mc.csv`, set `ratio`):

|---|---|---|---|---|---|---|
| 8 | 8 | 1 | 1.000 | 1.000 | 1.000 | 1.000 |
| 8 | 4 | 2 | 0.574 | 0.146 | 0.577 | 0.692 |

for that model and SLO. That is our arithmetic on their numbers. The 1:1 to
1:3 range is an assumption, not a value from DistServe or Splitwise.

At D=72 the spill appears only near saturation, and it is the classic
trunking effect. A rack's 6 x c local slots behave like an Erlang loss
system, so small c (few slots per rack) spills earliest. The three

the code trace's burstiness (inter-arrival CV 13.2 for one front end).
Where they differ (code at c=4 and c=64, rho >= 0.8), the code trace's
heavy-tailed output lengths are the cause, and its CIs are 3-10x wider.

## 5. Offered load at native trace speed and headroom

ft1152, TP=8, prefill:decode 1:2, mixed layout, conv trace: 16.7 Gbps of KV
in total (`results/e7/e7_load.csv`).

| fabric | D | policy | fabric Gbps (same pod / cross-pod) | k_core | k_any (binds) | fabric-limited req/s |
|---|---|---|---|---|---|---|
| 1:1 | 8 | random or locality | 16.74 (0.92 / 15.82) | 12,766 | 4,588 (NIC) | 25,372 |
| 1:1 | 8 | rail-aligned | 16.74 (15.82 / 0) | inf | 4,588 (NIC) | 25,372 |
| 1:1 | 72 | random | 15.69 (0.28 / 15.41) | 13,049 | 4,894 (NIC) | 27,063 |
| 1:1 | 72 | locality-aware | 0 | inf | inf | inf |
| 4:1 | 8 | random or locality | 16.74 (0.92 / 15.82) | 3,191 | 1,147 (ToR) | 6,343 |
| 4:1 | 72 | random | 15.69 (0.28 / 15.41) | 3,262 | 1,223 (ToR) | 6,766 |
| 4:1 | 72 | locality-aware | 0 | inf | inf | inf |

For the 4:1 rows, `fat_tree_1024_4os` oversubscribes the ToR tier, so the
ToR uplinks bind before the pod uplinks. On ft128, whose 4:1 sits at
agg->core, the core binds: k_core = 131 for D=8 and k_any = 239 (NIC) on
1:1. Other traces scale inversely with their mean KV rate:

- fixed4k (59.4 Gbps): all k values are 3.55x smaller.
- code (13.8 Gbps): 1.21x larger at the mean.
- The code trace's p99 one-second bin is 151 Gbps, 11x its mean, so a
  single front end's bursts eat an order of magnitude of headroom.

**Reading these numbers.** One Azure trace is one front end, and at its
native rate it is far below any fabric. The multipliers are in thousands
because the question they answer, "when does the fabric saturate on
average", is not where KV transfers hurt. A rough estimate of what the GPUs
themselves can generate makes the point:

- Prefill costs about 2 x 70.6 G = 141 GFLOP/token.
- 8 x H100 at 989 dense BF16 TFLOP/s and an assumed 40 % utilization gives
  about 22k tokens/s per TP=8 prefill instance.
- That is 22.4k x 327,680 x 8 = 59 Gbps of KV per instance, about 7 Gbps per
  200 G NIC on average.

Mean NIC utilization from KV is single-digit percent. The cost is the
*burst*: each 4K request is 1.34 GB that must arrive before decode can
start. At 8 x 200 G that takes 6.7 ms at line rate, and incast and ECMP
collisions stretch it (E1-E6). These are order-of-magnitude assumptions,
not measurements. The point is that E7's headroom says the fabric has
capacity on average, while the project's experiments measure how badly it
uses that capacity per transfer.

**Rail-aligned TP=4 at 1:1.** In the mixed layout at 1:1, every node holds
the decode instance on GPUs 0-3 and the prefill on GPUs 4-7, so no prefill
can find a decode instance on its rails. Rail-aligned then falls back to
random and 94-99 % of bytes cross the core at D <= 72
(`e7_crosspod`, top-left panel). D = 36 is the exception: its 9 instances
per domain shift the offsets from domain to domain.
Rail alignment and two-instances-per-node packing conflict unless the
layout varies the offsets. The shuffled layout gives cross-pod 0.000 for
rail-aligned at TP=4.

## 6. How the papers enter

- **DistServe (Zhong et al., OSDI 2024).**
  - Used: its low node-affinity placement keeps prefill and decode segments
    within a node to use NVLink. That is our locality-aware policy in the
    one setting where it works by construction.
  - Used: its single-GPU OPT-13B rates (1.6 colocated, 5.6 prefill, 10
    decode req/s), as quoted in `docs/PROJECT.md`, only to motivate the 2:1
    row.
  - Not used: no other DistServe number.
- **Splitwise (Patel et al., ISCA 2024).**
  - Used: the Azure 2023 conversation and code traces in `data/azure/`,
    which were released with it.
  - Used: the deployment shape of separate machine pools for the prompt and
    token phases, which is our pooled layout and the D=8/TP=8 row.
  - Not used: no provisioning ratio or other number from it.
- **Mooncake (Qin et al., FAST 2025).** Cited for the production deployment
  shape: separate prefill and decode pools, with KV moved over GPUDirect RDMA by its
  Messenger component. No number is taken from it.
- **Everything else is an assumption, stated in section 1:** ratios, c,
  rho, TPOT, the rail count, the cluster sizes and the H100 FLOP estimate.

## 7. Reproduce

    scripts/e7_scaleup.py                      # ~17 min on one core; tables to stdout
    scripts/e7_scaleup.py --no-mc              # closed form + load tables only, ~2 s
    scripts/e7_scaleup.py --fig-only           # redraw figures from the CSVs
    scripts/e7_scaleup.py --quick --reps 3     # smoke run

Outputs:

| file | contents |
|---|---|
| `results/e7/e7_closedform.csv` | every cluster x D x TP x ratio x layout x policy, c = inf: off-fabric fraction and the ToR / pod / core split |
| `results/e7/e7_load.csv` | native-rate Gbps per tier, busiest pod uplink, k_core, k_any, binding resource, max req/s, per trace and 1:1 / 4:1 fabric |
| `results/e7/e7_shuffled.csv` | random role layouts, mean and 95 % CI |
| `results/e7/e7_mc.csv` | MC points (sets `figure`, `headline`, `check_cinf`, `capacity`, `ratio`), each with closed-form and fluid references, 95 % CIs, spill and overflow rates |
| `results/figs/e7_offfabric.{png,pdf}` | bytes on the fabric vs D |
| `results/figs/e7_crosspod.{png,pdf}` | bytes on pod uplinks vs D |

The MC is deterministic for a given `--reps` (seeds 11.., layouts 1000..).
No simulator run is involved.
